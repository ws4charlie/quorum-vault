# Gate 授权凭证

[English](../gate-credential.md)

AgentGate 决定 AI 智能体能不能付款，QuorumVault 持有能付款的密钥。Gate 授权凭证是把两者连起来的唯一文件：一份短寿命、带签名、只对一笔付款有效的许可。签名区只有在凭证验证通过时，才会签 Gate 管控钱包的付款。本页是合同：AgentGate 和 QuorumVault 各自按本页和共享的[测试向量](#测试向量)实现自己这一侧，互不引用对方的代码。

状态：验证包、测试向量、EIP-3009 类型和签名区的检查（第 0 到 13 项，网关和每个协签程序都执行）已完成。签名接口已支持 `evm_eip3009`；`evm_transfer` 留给后续版本。

## 凭证

一个 JSON 对象。每个字段都必须有；表里没有的字段一律拒绝。

| 字段 | 类型 | 格式与限制 |
|:---|:---|:---|
| `v` | 整数 | `1`。其他值拒绝 |
| `kid` | 字符串 | Gate 签名密钥的编号。1 到 64 个字符，取自 `A-Z a-z 0-9 . _ -` |
| `credential_id` | 字符串 | 每份凭证唯一。小写 UUID 文本，`8-4-4-4-12` |
| `obligation_id` | 字符串 | Gate 给这笔付款的编号；一笔付款可以有多份凭证。不透明。1 到 128 字节的 UTF-8 |
| `audience` | 字符串 | 目标 Vault 部署，例如 `qv-staging`。1 到 64 个字符，取自 `a-z 0-9 . _ -`，以字母或数字开头 |
| `wallet_id` | 字符串 | 付款钱包在 Vault 里的编号。小写 UUID 文本 |
| `chain` | 字符串 | CAIP-2 链编号。第 1 版只有 `eip155:<十进制编号>`，不带前导零，例如 `eip155:84532` |
| `asset` | 字符串 | `native` 表示该链的原生币，否则是代币合约地址：`0x` 加 40 位小写十六进制 |
| `payee` | 字符串 | 收款方：`0x` 加 40 位小写十六进制。大小写混合（校验和）的写法拒绝，所以只有一种写法 |
| `amount` | 字符串 | 整数最小单位（wei、代币最小单位），十进制数字：无符号、无前导零、无小数点、至少为 1、不超过 2^256 − 1。这是格式的上界，不是付款的上界：Vault 还会拒绝超过该钱包此资产单笔限额的金额（见快速通道） |
| `issued_at` | 整数 | Unix 秒，至少为 1 |
| `expires_at` | 整数 | Unix 秒，晚于 `issued_at` |
| `policy_version` | 字符串 | 不透明。1 到 64 字节的 UTF-8 |
| `decision_reason` | 字符串 | 不透明。1 到 256 字节的 UTF-8 |
| `sig` | 字符串 | 签名（见下）。不在被签名的字节里 |

凡是 Vault 要比较或用作标识的字段，都是严格的 ASCII，见上表。三个不透明字段 `obligation_id`、`policy_version`、`decision_reason` 原样携带 Gate 手里的内容：任何合法的 UTF-8，逐字节保留，不做规范化（预组合和分解形式的 é 是两个不同的字符串），长度按字节计，不按字符计。控制字符（U+0000 到 U+001F）和非法 UTF-8 拒绝；写成转义、又不成对的 UTF-16 代理项也拒绝。Vault 从不解读这些字段：原样记录，原样写入审计记录。整数用普通十进制写法，且小于 2^53，所以两侧都能精确表示。超过 4096 字节的凭证拒绝。

解析是严格的。字段重复、出现未知字段、缺字段、值的 JSON 类型不对（金额写成数字、时间写成字符串）、数字带符号、小数点或指数，以及对象之后还有文本，都拒绝。未知字段绝不忽略：以后增加字段必须同时提升 `v`。

## 编码与签名

**编码：JSON 规范化（RFC 8785）。** 两侧都会处理 JSON，这条规则是标准，各语言都有现成的库。成员名全是 ASCII，所以该标准按 UTF-16 码元排序就等于按字节排序。数字是小于 2^53 的非负整数，用普通十进制。字符串严格按该标准处理：引号和反斜杠转义（`\"`、`\\`），控制字符用短写法（`\b \t \n \f \r`）或小写的 `\u00xx`，其余字符都以 UTF-8 原样写出，包括 U+FFFF 以上的字符和 U+2028。（会转义 U+2028 或非 ASCII 文本的库不符合 RFC 8785。）测试向量对每一点都有用例。固定字段顺序同样安全；选 JCS 是因为以后版本增加字段时不需要新的顺序表。

**签的是什么。** 字节 `qv-gate-credential-v1`、一个换行符，然后是去掉 `sig` 的对象的规范化形式。前缀把这些签名与这把密钥的其他用途隔开。

**信封。** 发送的凭证就是多了一个成员 `sig` 的对象：64 字节的 Ed25519 签名（RFC 8032），base64url 编码，不带填充。`sig` 的每个字节都必须在 `A-Z a-z 0-9 - _` 之内，且解码后恰好 64 字节：带填充、用别的字母表、含空白（包括有些解码器会跳过的换行和回车）、长度不对，都以 `credential_malformed`（字段 `sig`）拒绝。公钥按同一规则，长度 32 字节。验证方不信任收到的文本的顺序和排版：它解析、重新算出规范化形式、再验签。所以一份合法凭证被重排或加了空格，仍然通过。

**签名覆盖 `payee`、`amount`、`asset`、`chain`、`wallet_id`、`audience`、两个时间和不透明字段。** 签名后改动其中任何一个，签名都会失败。

## 密钥与轮换

Gate 用一把只为此用途存在的 Ed25519 密钥签名。Vault 只持有公钥。谁能加一把密钥，谁就能为每个 Gate 管控的钱包生成凭证，所以密钥集合的权限等同于审批人名册，也用同样的方式保管：它属于 Gate 管控钱包这一族设置，**由签名区管理员达到法定人数签名、带版本号，由网关和每个协签程序各自根据自己验证过的记录执行**。业务侧能写的任何地方都不放密钥。一条记录包含 `kid`、32 字节公钥（base64url，不带填充）、生效时间，以及可选的失效时间；检查方在验证时用自己的时钟得出当前可用的集合。配置文件里只放**初始集合**，在还没有任何签名记录时使用，与审批人名册里的初始审批人一样：签名的变更可以不重启就退役一把初始密钥，被退役的 `kid` 和密钥永不再用。初始集合为空、`kid` 不合规或密钥长度不对时，节点拒绝启动；受众名无效或一把密钥都没有的签名版本会被拒绝。

- **多把密钥可同时生效。** 轮换：一次签名变更加入新密钥；Gate 开始用它签名；之后第二次签名变更退役旧密钥（或设置它的失效时间），不早于旧密钥签出的最后一份凭证过期（最长寿命加偏差容限）。
- **未知的 `kid` 拒绝**，记为 `kid_unknown`；不在生效到失效时间之内的密钥同样如此。Vault 绝不会改试别的密钥，所以凭证无法自己选择由哪把密钥检查。凭证写了一把密钥却由另一把签的，记为 `signature_invalid`。
- **退役一把密钥**是一次签名变更。没有吊销列表：凭证只活几分钟。

## 签名区的检查

签名区里每个检查方按顺序执行，第一个失败就停止。每种失败都有稳定的错误码，写入审计记录并返回给调用方。没有任何开关、构建选项或设置能关掉检查。

| # | 检查 | 错误码 | 字段 |
|:--|:---|:---|:---|
| 0 | 钱包由 Gate 管控。给其他钱包带凭证一律拒绝，这样配置错误会立刻暴露 | `wallet_not_gate_governed` | |
| 1 | 带了凭证 | `credential_missing` | |
| 2 | 按上述严格规则能解析 | `credential_malformed` | 出错的字段 |
| 3 | `kid` 在密钥集合里 | `kid_unknown` | `kid` |
| 4 | 签名对被签字节验证通过 | `signature_invalid` | |
| 5 | `audience` 等于本部署的名字 | `audience_mismatch` | `audience` |
| 6 | `wallet_id` 等于付款钱包 | `wallet_mismatch` | `wallet_id` |
| 7 | `expires_at − issued_at` 不超过最长寿命 | `ttl_too_long` | `expires_at` |
| 8 | `issued_at` 不晚于现在 + 偏差容限 | `not_yet_valid` | `issued_at` |
| 9 | 现在早于 `expires_at` + 偏差容限 | `expired` | `expires_at` |
| 10 | `chain`、`asset`、`payee`、`amount` 依次与签名区从将要签名的字节里解析出的值相等 | `payment_mismatch` | 第一个不同的字段 |
| 11 | EIP-3009：授权自己的有效期落在凭证的有效期之内 | `authorization_window` | |
| 12 | 本检查方此前没有用过这个 `credential_id`；记录与决定在同一个事务里写入 | `replayed` | |
| 13 | 付款在该钱包的快速通道限额之内 | `fast_lane_cap` | |

第 1 到 11 项是纯计算（验证包）；第 0、12、13 项用每个检查方自己的状态。签名区不信任载荷以外的任何东西：第 10 项比较的是签名区自己解析出的值，绝不是请求里的字段。

**拒绝原因。** 被拒绝任务的原因是 `<code>: <detail>`，表里列出字段时是 `<code>: field <field>: <detail>`，错误码与上表相同、不做改动。两方签名时，网关自己的拒绝按这个格式写入任务；网关接受后被协签程序拒绝的，记为 `signer_refused`，里面带协签程序的原因。

**时钟。** 每个检查方用自己的时钟。偏差容限默认 30 秒，可配置到最多 5 分钟；它同时放宽窗口的两端。

**最长寿命。** 默认 10 分钟，可在 1 秒到 1 小时之间配置。凭证在被使用前是持有即可用的许可，寿命越短，被偷的凭证越不值钱，重放记录也越短。Gate 生成并调用只需要几秒；几分钟足够重试一次。

## 凭证绑定的内容

Vault 解析将要签名的载荷，从字节里得到付款 `{chain, asset, payee, amount, wallet_id}`。字符串按原样逐字比较，地址由签名区先转成小写。

| 付款类型 | `chain` | `asset` | `payee` | `amount` | 条件 |
|:---|:---|:---|:---|:---|:---|
| EVM 原生币转账 | 交易的链编号 | `native` | `to` | `value` | 没有调用数据 |
| EVM 代币转账 | 交易的链编号 | `to`（代币合约） | `transfer(address,uint256)` 的第一个参数 | 第二个参数 | `value` 为 0；调用数据恰好是这个调用；`approve`、`transferFrom` 等其他调用不能凭证付款 |
| EIP-3009 `transferWithAuthorization`（在 x402 任务里实现） | `domain.chainId` | `domain.verifyingContract` | `to` | `value` | `from` 是付款钱包的地址；`validAfter` 不早于 `issued_at`，`validBefore` 不晚于 `expires_at`；`validAfter` 早于 `validBefore` |

一份凭证只付一笔款。同一个 `credential_id` 配第二个载荷，拒绝。

## Gate 管控的钱包与快速通道

**Gate 管控的钱包**由签名区的一项签名设置标记：需要签名区管理员达到法定人数签名，带版本号，网关和每个协签程序都执行。Gate 管控的钱包没有经过验证的凭证，任何路径都不能付款。设置里每个钱包由 `wallet_id` 和一个热钱包分区指定；签名区管控的是这个分区所在的整个热钱包分片，包括它的每种资产和每一代密钥，所以换一种资产或换一把密钥都绕不开凭证。这类钱包不签批量付款。其他钱包规则不变。**内部转移**（归集、补充、清空、转冷钱包、合并、再平衡）不需要凭证。

凭证验证通过后，Gate 管控钱包的付款不需要人工审批（Gate 的批准就是批准，随付款送来的审批一律忽略），签名区自己的提现规则（目的地址、上限、频率）仍然有效，前提是同在这项签名设置里的三个限额都没有超；限额按钱包和资产分别设置，单位是该资产的最小单位：

| 限额 | 含义 |
|:---|:---|
| 单笔 | 单笔 `amount` 的最大值 |
| 每小时 | 过去 60 分钟内仅凭证付款的总额 |
| 每天 | 过去 24 小时内仅凭证付款的总额 |

超过任何一项限额，付款被拒绝，记为 `fast_lane_cap`；这一版没有退回人工审批的路径。没有设置限额的资产，三项都是 0。单笔限额同时是付款金额的上界：格式允许到 2^256 − 1，Vault 不允许。已签名的授权从签名区签出时开始计数，而不是等到链上使用。每个检查方用自己的记录计数，任何一个拒绝，签名就不会产生。

## 签名接口

调用方向是 Gate 调 Vault；Vault 从不调 Gate。核心只提供这一个调用，自己不做决定：凭证放在签名任务里送到签名区，每个检查方按上面的检查，对照自己解析出的内容核对。

**调用方。** AgentGate 服务，同时出示两样证明：它的客户端证书，名字是 `spiffe://quorumvault/business/agentgate`，由 Vault 的业务区证书机构签发；以及 Vault 身份提供方签发的客户端凭据令牌，带角色 `gate`。这个角色只允许这一个调用。持有这个角色、或出示这张证书的调用方，在其他所有接口上都被拒绝，记为 `client_not_authorized`；这个接口也以同样方式拒绝其他所有调用方。

**请求。** `POST /v2/gate/signatures`，一个 JSON 对象。出现其他成员即被拒绝。

| 成员 | 取值 |
|:---|:---|
| `wallet_id` | 付款的 Gate 管控钱包。小写 UUID 文本 |
| `kind` | `evm_eip3009`。`evm_transfer` 留给后续版本，现在记为 `request_invalid` 拒绝 |
| `payload` | `evm_eip3009` 时：授权的 EIP-712 类型化数据（见下） |
| `credential` | 凭证，作为 JSON 对象（不是字符串） |

**`evm_eip3009` 的载荷。** `eth_signTypedData_v4` 形式的类型化数据：一个对象，恰好含 `types`、`primaryType`、`domain`、`message`。

| 成员 | 取值 |
|:---|:---|
| `types` | 恰好两项。`EIP712Domain`：`name` string、`version` string、`chainId` uint256、`verifyingContract` address。`TransferWithAuthorization`：`from` address、`to` address、`value` uint256、`validAfter` uint256、`validBefore` uint256、`nonce` bytes32。都按这个顺序 |
| `primaryType` | `TransferWithAuthorization` |
| `domain` | 代币合约的 `name` 和 `version`（Base Sepolia 上的 USDC：`USDC`、`2`），`chainId` 是 JSON 数字，`verifyingContract` 是代币地址 |
| `message` | 每个值都是字符串。`from`、`to`：`0x` 地址，全小写或校验和正确。`value`、`validAfter`、`validBefore`：不带前导零的十进制。`nonce`：`0x` 加 64 位十六进制 |

`from` 必须是付款钱包的地址，代币必须是这个钱包的资产。`validAfter` 早于 `validBefore`，`validBefore` 在未来、且离 Vault 时钟不超过该代币的最长窗口，并且窗口落在凭证的有效期内（第 11 项检查）。Vault 签的是它按这些值重新构造的类型化数据，而不是收到的字节。被拒绝的授权，其 EIP-3009 `nonce` 仍记在 Vault，所以重新尝试时，除了新凭证，还要换一个新的 nonce。

**响应。** 成功返回 200，带 `credential_id`、`wallet_id`、`kind` 和 `signature`：`r`、`s`、`v` 连在一起，65 字节，`0x` 十六进制，`s` 取低值，`v` 为 27 或 28。这正是 `transferWithAuthorization` 和 x402 接受的形式。拒绝时返回一个对象，含 `code`、有则带 `field`，以及 `message`；绝不返回签名。

| 状态码 | 错误码 |
|:---|:---|
| 400 | `request_invalid`、`credential_missing`、`credential_malformed` |
| 401 | `client_not_authorized`：没有有效令牌 |
| 403 | `client_not_authorized`、`wallet_not_gate_governed`、`kid_unknown`、`signature_invalid`、`audience_mismatch`、`wallet_mismatch`、`ttl_too_long`、`not_yet_valid`、`expired`、`payment_mismatch`、`authorization_window`、`fast_lane_cap` |
| 409 | `replayed` |
| 422 | `payload_invalid`（载荷无法解析成这个钱包、这个类型的付款） |
| 503 | `retry_later`：还没有任何决定（签名区在等待时间内没有答复、资金还没空出来、某个存储连不上）。`signing_failed`：签名区的签名程序出错，或签名区以本表没有列出的理由拒绝 |

**核心检查什么。** 只做代价小、且只会拒绝的检查：请求的形态；钱包在核心自己的配置里是 Gate 管控钱包；凭证能解析，指向本部署和这个钱包，新请求的凭证还没过期；载荷按上面的规则能解析；单笔限额和付款分片的可用资金。签名区的拒绝原样带回签名区的错误码和字段。

**按 `credential_id` 幂等。** 同一个请求再来一次（`wallet_id`、`kind`、`payload` 和凭证都相同；JSON 的排版不影响）返回已保存的答复，或者等待同一个签名任务：绝不会产生第二个任务。同一个 `credential_id` 配不同的请求，记为 `replayed` 拒绝。成功的答复，以及每一个来自决定的拒绝（4xx 和 `signing_failed`），都会保存，重复请求时原样返回；Gate 要再试，就生成一份新凭证，用新的 `credential_id`。`retry_later` 不保存：同一个请求可以再发，继续同一个任务。如果签名已经产生、但答复丢了，重试同一个请求会拿到它：核心从任务中读出签名，不会第二次签名。

## 重放记录与审计

每个检查方在自己的守卫数据库里记录它接受的每个 `credential_id`，与占用这笔付款在同一个事务里完成，第二次使用会被拒绝（先用者胜，原子完成）。记录保留到 `expires_at` + 偏差容限 + 1 天；清理不会删掉仍可能通过验证的记录，多出的一天用于排查问题。业务核心自己有一张表，用于接口的幂等，它不是规则本身。检查方在首次使用时记录 `credential_id` 和载荷的摘要；之后同一个 `credential_id` 的任何使用，不论载荷是什么，只要付款检查通过，都记为 `replayed`（载荷解析成另一笔付款的，先得到 `payment_mismatch`）。只记录被接受的凭证，所以伪造的凭证用不掉真实的 `credential_id`。同一个载荷再来一次，是同一次签名的重试，不算第二次使用：网关返回它保存的签名，协签程序再次允许同一个摘要；两者都不写新记录，也不重复计数。同一个已用 `credential_id` 下的其他任何载荷都记为 `replayed`。

每次接受和每次拒绝，都与决定在同一个事务里写入检查方的审计记录：`credential_id`、`obligation_id`、`policy_version`、`decision_reason`、`wallet_id`、付款内容、错误码和字段，以及是哪个检查方。无法解析的凭证只记录大小和哈希，因为它的文本不可信。

## 测试向量

`testdata/gate-credential/vectors.json` 包含一个固定时钟、两把密钥（带 `kid`）的密钥集合，以及若干命名用例；每个用例有确切的凭证文本、十六进制的被签字节、签名区解析出的付款，以及预期结果和错误码。内容涵盖每种付款类型的合法凭证、由第二把密钥签的凭证、上文所有不需要状态的拒绝情形，不透明字段的 UTF-8 用例（非 ASCII 字母、U+FFFF 以上的字符、引号和反斜杠，以及被拒绝的控制字符和非法 UTF-8），还有重放用例：同一份凭证用两次，以及换了载荷再用。AgentGate 原样复制该文件；两个仓库都必须通过每个用例。密钥由公开字符串推导而来，并标明仅供测试；两个仓库里再没有任何属于这份合同的密钥材料。
