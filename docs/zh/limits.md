# 局限

[English](../limits.md)

本页列出 QuorumVault 目前做不到的事，省得你踩了坑才发现。

**没有真正跑过**
- **只在本地链上跑过。** 测试用的是本地 EVM 节点、Bitcoin regtest 和本地 Solana validator。没遇到过真实的手续费市场、深度重组或拥堵的网络。
- **没上过测试网或主网。** 不要把它指向真实资金或真实密钥。
- **只在一台笔记本上压测过。** 有本地压测（[结果](../measurements/load-local.md)），用本地链、SoftHSM，所有进程在同一台机器上。没有在集群上、带真实网络延迟、用硬件 HSM 或真实链做过，所以没有哪个数字能当容量规划。
- **还没有真实的集群运行过这些 chart。** 四个集群的形态是一个设计，由测试检查过（见[部署](deployment.md)）。
- **第一次镜像发布还没有做。** 镜像会构建和检查，但没有发布。
- **恢复演练只在一台机器上做过**，没有跨机房。
- **在支付凭证检查落地之前（GATE-CONNECT，GC2），所有构建都拒绝 x402 许可。** 签名区会解码并检查它们，测试用只存在于测试代码里的规则来签。同样的原因，CI 里没有让两方 MPC 签名方签这类许可：它的协签程序需要那条规则。只有本地的 84532 链节点见过它们，没有在公共的 Base Sepolia 上运行过（见[运维手册](../runbooks/x402-hot-wallet.md)，英文）。

**模拟的部分**
- **CloudHSM 的支持还没有在硬件上验证过。** 参与方的封存模块有一套 AWS CloudHSM 的配置，只对照文档和测试替身验证过，没有在真实集群上运行过；第一次运行按[检查清单](../runbooks/cloudhsm-sealer.md)（英文）进行。
- **用的是 SoftHSM，不是硬件。** 令牌是软件，没有防篡改能力。结构上是真 HSM 需要的那一套，但它不是真 HSM。
- **M-of-N 是模拟的。** 冷钱包签名机用软件检查冷钱包签名人的签名；硬件 HSM 会自己强制执行这条规则。
- **飞地是模拟的。** 证明由一个替身产生，所以没有人证明过真实硬件度量的结果和替身一样（见[飞地](enclaves.md)）。
- **AWS Nitro 路径还没有在硬件上运行过。** 证明方、通过 AWS KMS 放出密钥、以及密钥策略，只用替身和一份真实的 AWS 证明文档测试过。参与方目前还不能在飞地里运行：还缺网络桥接、经 vsock 的存储和协签程序的通路。密钥策略没有时钟，所以过期的程序要重新应用策略才会被移除；证明的证书链只对照 AWS 的根检查，不检查吊销（见 [Nitro 首次运行](../runbooks/nitro-first-run.md)）。
- **撤销一个程序不会立刻让它停下。** 正在运行的参与方把密钥留在内存里直到重启，也没有机制让它再来问一次。要马上切断，运营人员还要同时停掉它（见[飞地](enclaves.md)）。
- **还没有任何真实集群运行过飞地的 chart。** 密钥代理的 chart 和参与方的飞地模式，目前只由测试检查，之后会在本地集群里用模拟的飞地检查。chart 在开发和测试之外仍然拒绝飞地模式的参与方：Nitro 证明方已经写好，但还没有在硬件上运行过。
- **服务身份是模拟的。** 两个证书颁发机构由脚本在开发者的机器上生成，密钥放在文件里。生产环境必须自带 PKI 和证书管理器（见[证书运维手册](../runbooks/certificates.md)，英文）。指标走明文 http，只能在本机访问。
- **所有参与方运行在一台机器上，由同一个团队运行。** 密码学上的隔离是真的，运营上的隔离不是。

**审批和登录**
- **登录和审批是用软件部件测的。** 测试用户和开发用的身份提供方都是测试数据，测试里用软件密钥批准。没有试过真实的硬件密钥，不管是在浏览器里还是在命令行工具里。审批页面只在无头浏览器里运行过。
- **"看到什么就签什么"只解决了一部分。** 安全密钥签的是一个哈希，没有屏幕。审批页面会重新计算哈希，能发现说谎的核心，但被替换的页面仍然可以显示一个收款人，却让密钥签另一个任务。大额付款用命令行工具更好，因为它在单独的机器上打印所有字段；但没有任何密钥带显示屏，所以人仍然要信任那台机器（见[运维手册](../runbooks/webauthn-approver.md)，英文）。要堵上这个缺口，需要能自己显示任务内容的设备，这还没有做。
- **每个审批人名字只能有一把密钥。** 一个人想要第二把密钥，就得再用一个名字。
- **审批的端到端测试只用 HSM 签名方式运行。** MPC 模式下不运行它。
- **能写业务数据库的人可以通过手续费上限记录让提现停住，但改变不了签名区签什么。** 核心把自己的手续费上限记录当作提示来用，不检查签名；签名区按自己的记录判断每一笔付款，其余的一律拒绝（见[运维手册](../runbooks/btc-fee-caps.md)，英文）。
- **签名区管理员是签名区设置里的一份短名单。** 它是审批人变更的信任根，所以改名单要改设置并重启。不再满足调高后规则的旧变更会被忽略。

**签名和参与方**
- **参与方管理员密钥是软件密钥。** 参与方的管理调用（密钥设置、刷新、解锁）需要多名管理员共同签署同一份请求，请求写明这次调用做的所有事。每名管理员把密钥放在自己的机器上；暂不支持硬件密钥。名单本身现在通过现任管理员签名的请求来改，设置里的名单只是起始名单。如果管理员凑不够人数，要回头就得三个参与方的平台运维人员一起动手，并伴随一次停机（见[手册](../runbooks/key-ceremony.md)，英文）。旧的单签名格式只在参与方设置仍允许、且没有改过名单时才可用。
- **更换恢复密钥是一场仪式，工具负责跟踪，不替人执行。** 参与方拒绝用已退役密钥做的备份，状态命令会显示还差什么；但新密钥的生成、逐个密钥组的刷新、销毁旧备份和旧密钥，仍由保管人手动完成。留在进程之外的备份副本，工具看不到。**新的恢复密钥加刷新，挡不住已经拿到旧密钥和旧备份的人：** 他们仍能重建签名密钥，在参与方之外签名。如果两者都可能泄露，必须更换钱包密钥并转移资金（见[手册](../runbooks/mpc-backup-restore.md)，英文）。
- **封装密钥只有在参与方自己有 PKCS#11 令牌时才能在 HSM 内原地更换。** 它解决的是策略变了或旧密钥可能有副本的情况，解决不了仍然能使用令牌的攻击者。从密钥代理取密钥的参与方，目前还不能更换代理的封装密钥：代理没有这个调用（见[手册](../runbooks/key-ceremony.md)，英文）。
- **有些回滚发现不了。** 如果两个参与方都被恢复到同一个更早的代，没有任何东西会察觉。一个参与方被恢复到同一代的更早状态，可能会把重复的任务再签一次。密钥代理没法销毁旧几代的密钥（见[飞地](enclaves.md)）。
- **新密钥在接手之前不会先试签。** 激活后的第一次真实签名，才是它能用的第一个证明（见[密钥更换](key-replacement.md)）。
- **cb-mpc 没有在这里经过外部评审。** 所以任何密码学失败都会让密钥锁定。
- **锁定可能晚一步才到达某个成员。** 三个参与方之间的锁定通知是尽力而为的。如果某成员发现了篡改，它给协调方的结论丢了，给第三个成员的通知也丢了，协调方又问不到该成员，那么协调方和第三个成员在遇到已锁定的成员之前，仍可以一起签名（见[手册](../runbooks/mpc-keyset-freeze.md)，英文）。
- **协签程序连上一个空的防重放数据库时，分不清它是新装还是丢了数据。** 它会在没有重放历史和审计链的情况下启动，数据库配置错了或从空白恢复后，相关检查会悄悄变弱，直到有人发现（见[证书运维手册](../runbooks/certificates.md)，英文）。
- **手续费高时，小额充值会留在充值地址上。** 只有资金价值超过归集手续费的 `k` 倍才会归集；资金已入账，是安全的，手续费降下来或有更多资金到账时就会归集。对账视图会显示原因，等得太久会触发报警。没有亏本归集的命令（见[手册](../runbooks/unswept-deposits.md)，英文）。
- **两方密钥需要两个参与方都在。** A 或 B 宕机时，Bitcoin 和 Solana 充值的归集会暂停。
- **更换 Solana 热钱包时，提现会短暂暂停。** 新密钥在启用并拿到资金之前不能创建 nonce 账户，所以从切换到运营人员创建好之间，新的提现要等待。配置里没有列出的代币，以及不是标准形式的代币账户，只会被报告，不会被转走（见[密钥更换](key-replacement.md)）。
- **Solana 的紧急清空按资产列表的顺序转代币，不按价值排序，** 只在本地验证节点上跑过；其余部分先转 SOL，新的 nonce 池由运营人员随后创建（见[热钱包密钥被盗运维手册](../runbooks/stolen-hot-key.md)，英文）。
- **紧急情况下，窃贼先转走的钱救不回来。** 旧密钥在链上一直有效，只有签名区会拒绝它；把充值指向新密钥的密钥仪式要几个小时，归集期间暂停；紧急演练只在本地链上跑过（见[热钱包密钥被盗运维手册](../runbooks/stolen-hot-key.md)，英文）。
- **被盗的 Solana 密钥上可能已经签名的付款会挡住紧急清空，而且没有命令可以结束等待。** 该笔付款的所有者被挂起，清空要等已签名的消息上链；要放弃它，目前没有运营命令（见[热钱包密钥被盗运维手册](../runbooks/stolen-hot-key.md)，英文）。签名前就被拒绝的付款，或签名区已占用 nonce 后被协签程序拒绝的付款，不会挡住清空。
- **Bitcoin 上被拒绝的 CPFP 子交易仍会占住一枚币。** 第二个签名方拒绝了子交易，签名区会一直保留对那笔卡住付款的找零的占用。EVM 和 Bitcoin 上现在失陷的密钥可以取消被拒绝付款的占用（Bitcoin 上这些币回到同一个旧热钱包，下一次转移会带走它们；其余的币立即转出）。被拒绝的 CPFP 子交易核心不会构造取消：转移会把这枚币排除在外并说明，由运维人员取消（见[热钱包密钥被盗运维手册](../runbooks/stolen-hot-key.md)，英文）。Solana 没有这种情况（见上一条）。
- **Gate 授权凭证目前只有一侧做了实现。** [规范](gate-credential.md)、共享的测试向量和一个验证包已经有了；签名区还没有执行它，AgentGate 也还没有实现自己这一侧或跑过这些向量。

**各条链**
- **Bitcoin 每个池只有一个热钱包分片**，所以没有再平衡。不支持 Taproot 地址，因为签名库派生不出来（见[调研笔记](../spikes/btc-taproot.md)，英文）。
- **批量的 Bitcoin 付款是看得出来的。** 链上能看出收款人是一起被付款的。
- **Solana 的覆盖更窄。** 只认经典的代币程序，客户数量很大时扫描方式也得换；冷钱包上用最近区块哈希签名的密钥仪式，必须在它的短寿命内完成。
- **冷钱包地址靠配置固定，不是签名设置。** 换新冷钱包密钥是一次要重启的、经过复核的部署（签名区和核心服务都要改）；两边都改完之前，热转冷会被拒绝并稍后重试。Bitcoin 的冷转冷没有找零输出，所以不能加价重发；输出很多的地址要分几轮转。Solana 上，旧地址在最后一步之后才收到的款项，要先对旧地址重新做一次冷钱包初始化才能转出（见[运行手册](../runbooks/cold-key-replacement.md)）。
- **EVM 和 Bitcoin 的每个冷钱包地址，同一时间只能有一个补充申请**（Solana 是每种资产一个）；Solana 的热钱包注资由运营人员的调用记账，不是由扫描发现的。
- **AgentGate 只能申请 x402 许可。** 它的签名接口还不能签普通转账；核心也无法把自己的 Gate 管控钱包清单与签名区的签名设置比对：两者由运维人员保持一致（见[运维手册](../runbooks/agentgate-client.md)，英文）。

**审计**
- **测试里用的一次写入存储，没有独立的合规评估。** 它只证明我们的代码能配合存储接口，不构成合规声明；生产打算用 AWS S3 Object Lock（见[调研笔记](../spikes/audit-worm.md)，英文）。

**部署**
- **AWS 参考部署从未被真正部署过。** 它是在没有账号的情况下检查过的代码（格式、校验、对隔离规则的模拟测试、静态检查和扫描）。第一次真实运行、费用，以及只有真实账号才能说明的事项，见[运行手册](../runbooks/aws-first-deploy.md)。
