# 局限

[English](../limits.md)

先把 QuorumVault 目前做不到的事说清楚，省得你踩坑才发现。

- **只在本地链上跑过。** 测试用的是本地 EVM 节点、Bitcoin regtest 和本地 Solana validator。没遇到过真实的手续费市场、深度重组或拥堵的网络。
- **没上过测试网或主网。** 不要把它指向真实资金或真实密钥。
- **用的是 SoftHSM，不是硬件。** 令牌是软件，没有防篡改能力。结构上是真 HSM 需要的那一套，但它不是真 HSM。
- **M-of-N 是模拟的。** 冷钱包签名机用软件检查运维人员的签名；硬件 HSM 会自己强制执行。
- **所有参与方跑在一台机器上，由同一个团队运行。** 密码学上的隔离是真的，运维上的隔离不是。
- **cb-mpc 没有在这里经过外部评审。** 所以任何密码学失败都会让密钥冻结。
- **登录和通行密钥是用模拟的部件测的。** API 确实要求 OpenID Connect 令牌，但测试用户和开发用的 Keycloak 是测试数据，测试里的登录和审批用的是软件认证器。没有试过真实的硬件密钥，没有认证证明，用户验证也不是真人做的。审批页面只在无头浏览器里配虚拟认证器跑过。空闲超时由身份提供方强制，不是核心（见[身份](identity.md)）。
- **“看到什么就签什么”只解决了一部分。** 安全密钥签的是一个哈希，没有屏幕。审批页面放在独立的来源上，显示的文字由任务本身生成，并重新计算哈希，所以说谎的核心会被发现。被替换或被攻破的页面仍然可以显示一个收款人，却让密钥签另一个任务；签名区只能核对签名对应的是它收到的那个任务。要堵上这一点，需要能自己显示任务内容的设备，例如手机应用或带屏幕的密钥，这还没有做。
- **测试里用的一次写入审计存储 SeaweedFS，没有独立的合规评估。** 它只证明我们的代码能配合存储接口，不构成合规说法；生产打算用 AWS S3 Object Lock（见[调研笔记](../spikes/audit-worm.md)）。
- **服务身份是模拟的。** 两个证书颁发机构由脚本在开发者的机器上生成，密钥放在文件里，没有放进 HSM 或硬件支撑的 PKI。SPIRE 还没有做；续期靠重新运行脚本。生产环境必须自带 PKI（见[证书手册](../runbooks/certificates.md)）。签名各方之间的连接仍然用固定证书。核心 API、数据库、Kafka 和 Temporal 已经覆盖（Temporal 和归档存储只检查调用方证书是否来自业务区颁发机构；名字由 Temporal 前面的一道闸门检查，归档存储的调用方靠访问密钥识别）。指标是仅限本机的明文 http。MPC 各方之间仍然用固定证书。
- **核心为比特币手续费上限变更保留了一份自己的审批人密钥**（核心配置里的 `fee_caps_change.approvers`）。已签名的审批人变更只到签名区。新加的审批人要等核心配置里也列出他，才能签手续费上限变更；被撤销的审批人也得在那里手动删掉，否则核心会接受他的变更而签名区拒绝（见[运维手册](../runbooks/approvers.md)，英文）。
- **运维人员是签名区配置里的一份短名单。** 它是审批人变更的信任根，所以改它要改配置并重启。调高 `min_operators` 或移除某位运维人员后，不再满足规则的旧变更会被视为无效并忽略；`qv-approvers show` 会报告被忽略的行。
- **没有压测。** 数字是在笔记本上测的，不是目标硬件（见[实测数字](../measurements)）。
- **两方密钥需要两方都在。** A 或 B 宕机时，Bitcoin 和 Solana 存款的归集会暂停。
- **Bitcoin 每个池只有一个热钱包分片**，所以没有再平衡。不支持 Taproot 地址，因为签名库派生不出来（见[调研笔记](../spikes/btc-taproot.md)）。
- **批量的 Bitcoin 付款是看得出来的。** 链上能看出收款人是一起被付的。
- **Solana 的覆盖更窄。** 只认经典的代币程序，客户数量很大时扫描方式也得换；冷钱包上用最近区块哈希签名的仪式必须在它的短寿命内完成。
- **EVM 和 Bitcoin 的每个冷钱包地址同一时间只能有一个补充申请**（Solana 是每种资产一个）；Solana 的热钱包充值由运维调用记账，不是扫描发现的。
- **恢复演练只在一台机器上做过**，没有跨机房。
