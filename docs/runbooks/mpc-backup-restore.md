# Runbook: backing up and restoring an MPC party (mpc-party)

Scope: the two-party hot signer (cb-mpc): party A (coordinator) and party B (follower), shares sealed in each party's own HSM
token. Commands: `mpc-party backup gen-recovery-key | export | verify | restore`. Drill: `mpc-party/scripts/restore-drill.sh`.

## What a backup is, and the one warning

A backup is a file per party per keyset **generation**: the two secret scalars of the share encrypted with PVE (publicly
verifiable encryption) to a recovery key, plus the rest of the share blob encrypted to the same key. Anyone can check a backup
with public data (`verify`); only the recovery **private** key can open it.

> **Both parties' backups of one generation plus the recovery private key equal the whole signing key.**
> Never keep them together. Never keep the recovery private key on a party host.

## Roles and places

| Item | Who | Where |
|---|---|---|
| Recovery private key | cold-ceremony custodians, M-of-N split (the same ceremony as the cold tier) | offline, in the safe; never on a network host |
| Recovery public key | anyone | on each party host, in the repository of the runbook |
| Party A's backup files | operator of A | storage A-side (separate account/site from B's) |
| Party B's backup files | operator of B | storage B-side; **never** the same place as A's |
| HSM token PINs | each party's own operator | environment variable or a 0400 file, never in the JSON config |

Two different people (or teams) hold A's and B's backups. Nobody holds both plus the recovery key.

## Routine (after every DKG and every Refresh)

The service logs `keyset moved to a new generation: existing backups are STALE` and `Health` shows per keyset
`backup_generation` and `backup_stale`. A stale backup restores a share that no longer pairs with the peer (the restore is
refused, see below), so back up again every time:

1. On each party host: `mpc-party backup export -config <party.json> -keyset <id> -recovery-public recovery.public -out <id>-g<N>-<A|B>.backup`.
   It unseals the current generation through the party's HSM, writes the file, **verifies it immediately** (public data only) and
   records the verified generation. Check the line `written ... and VERIFIED`.
2. Move each file to its owner's storage. Delete older generations' files only after the new ones are verified.
3. Confirm with `Health` (both parties): `backup_generation == generation`, `backup_stale == false`.

## Restore (a party lost: host destroyed, disk gone, HSM token lost)

Precondition: the peer is running and healthy; the lost party's HSM token exists (or is re-created and the new wrap key
generated by `mpc-party` on first use; shares are sealed again under the new key by the restore).

1. Bring the recovery private key to an **offline** machine (M-of-N custodians present). That machine runs `restore`.
2. Fetch the lost party's backup of the **peer's current generation** (see `Health` of the peer: `generation`).
3. `mpc-party backup restore -config <target party.json> -recovery-private recovery.private -file <backup>`.
   The config names the target party's token and an **empty** data directory. The tool refuses: a backup of the other party, a
   non-empty data directory, a wrong recovery key, a tampered file.
4. Start the party. It reconciles with its peer (generations compared, a **self-test** signs with the restored share) before it
   serves. Until then the keyset answers `UNAVAILABLE`. Watch for `keyset reconciled and proven`.
5. Re-run `Derive` for the keys you use (key metadata lives in the data directory, not in the backup; it is public and
   deterministic). Job records (idempotency) of party A are not in the backup: copy `data_dir/jobs` and `data_dir/keys` of A
   to the A-side storage regularly if retries across a total loss of A must stay idempotent.
6. Take new backups (the restore does not change the generation, but verify the restored party is covered: `Health`).

### A stale backup is refused

If the backup is older than the peer's generation, the party stays unresolved and the log says, for example,
`party B is on generation 3 but party A is on 5 ... restore party B from a backup of generation 5`. Fetch the right generation
and restore again into an empty data directory. Nothing is signed with a stale share.

### If one backup is lost

- Lost only the **backup** of a party that is still running: take a new one now (`export`); there is no emergency.
- Lost a running party AND its backup, the peer is fine: you cannot restore it. Run a new DKG for a new keyset, move funds with
  the cold tier, and retire the old key. This is why backups are verified and drilled.
- Lost the recovery private key: backups are useless; take a new recovery key (`gen-recovery-key`) and export new backups of the
  current generation immediately from both running parties.

## Drill

Every quarter, and after every change to the tooling: `mpc-party/scripts/restore-drill.sh` (local stack, destroys party B,
restores it, signs; prints `PASS`). Once a year: a drill with the real custodians, the real offline machine and the real HSM
token for one party on a non-production keyset. Record the date, who attended, and the output.

## 2-of-3 keysets (A, B and C)

Each member backs up its **own** share: a file per member per generation (`"scheme":"ecdsa-2of3"`), the member's one secret scalar
under PVE to the same recovery key plus the share blob with the scalar wiped. **Any one member's backup is useless alone; two
members' backups of one generation plus the recovery private key equal the whole signing key.** Keep the three members' backups in
three different places, held by three different people, never two together. The routine is the same as above on all three hosts
(`export` after every DKG and Refresh; `Health` on A, B and C shows `backup_generation` and `backup_stale`).

### One member lost (host destroyed, disk or HSM token gone)

Signing continues without it (any two sign). There is no emergency; do this when convenient, the sooner the better because a
second loss leaves nothing.

1. Make sure the other two are healthy and agree on the generation (`Health` of A, B and C).
2. Offline machine, recovery private key: `mpc-party backup restore -config <lost member's party.json> -recovery-private
   recovery.private -file <that member's backup of the CURRENT generation>`. The config names its token (`qv-party-3` for C) and an
   empty data directory. The tool refuses a backup of another member, a non-empty directory, a wrong recovery key, a tampered file.
3. Start the member. A reconciles all three and proves the keyset with the three-way self-test before it serves. If the backup is of an
   older generation, A logs `party C is on generation 2 but another party is on 3 ... restore it from a backup of generation 3`.
   The stale member stays out (it answers UNAVAILABLE and never signs) while the other two keep signing; fetch the right backup and
   restore again into an empty directory.
4. **Refresh the keyset** (operator-signed `Refresh` on A, all three online). The restored share becomes a new share on a new
   generation; the public key is unchanged. Refresh runs the self-test (every pair signs) before it commits.
5. Take new backups of the new generation from all three members.

If two members are lost at once, restore both from backups of the same generation (a single lost-member restore at a time is
safer), then refresh. If a member and its backup are both lost while the other two are healthy, you can still keep signing with the
two; run a new DKG to a new keyset and move funds, and retire the old key, before a second member can fail.
